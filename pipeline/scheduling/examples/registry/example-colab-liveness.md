# Colab session liveness — escalation body

You are working a failure ping from a `colab-liveness-<session>` scheduler entry. The checker (`bin/colab-liveness` in the colab-runner repo) runs every 15 minutes per live lease, reads only local files, and exits 3 only when something must be said: a finding that newly opened, an approval escalation crossing its threshold for the first time in its episode, or the all-clear. The ping's run output carries the `LIVENESS <session> <code> <detail>` lines. Your job is to route those lines — nothing else. 

Rules:

1. Read the session's state file `${WS}/colab-runner/var/liveness-<session>.json` (open findings with first-seen times, the lease's caller and host, work facts) and, if needed, the lease record `${WS}/colab-runner/var/lease-<session>.json`. Local reads only: never run a Colab wrapper, a lease verb, or anything that dials the session — dialing an approval-blocked host mints the very cards this schedule exists to prevent.
2. Routing table: `${WS}/colab-runner/config/notify-routes.json` maps a caller tag to a chat id under `routes`, with `main` as the fallback chat id.
3. `approval-outstanding` → the main chat, once. The checker speaks this code only on the first ping of a blocked episode, so if the state file's `approval_episodes` shows the episode already marked escalated AND a `reported` entry for it exists, this ping is a duplicate — stay silent. The message names the session, the host, the owning caller, and how long the approval has been outstanding.
4. Any other finding code (`binding-missing`, `host-divergence`, `deadline-missing`, `deadline-overdue`, `pulse-failing`, `pulse-stale`) → the owning thread: resolve the record's caller through the routing table; machinery callers (`panel`, `standing`, `test`, `lease`) and unknown callers go to the main chat. Before sending, read the owning thread's recent turns: if it has work queued or running for this session, say so in the message (a stalled session with work waiting is the urgent case); if the thread is visibly mid-recovery on the same stall, stay silent and just record it.
5. `cleared` → the same destination the finding it resolves was reported to (check the state's `reported` map); if nothing was reported, stay silent.
6. One short message per destination per ping: session, finding, since when, and what would clear it. No card content, no speculation about causes the local files don't establish.
7. Write back into the state file under `reported`: for each line you acted on, `{code, at, destination}`, and for each line you deliberately skipped, `{code, at, destination: "silent", reason}`. The checker's own dedupe is primary; this record is how the next ping's agent knows what was already said.
8. If the state file is gone or the lease record is gone, the session ended between the check and this ping — do nothing.
