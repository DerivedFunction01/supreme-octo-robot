# Runner review — colab-runner, for the superapp big-bang consolidation

Findings first:

- **The adapter seam already exists in fact.** Nearly every lease-core function takes the channel as its first parameter (`acquire(colab, repo, …)`, `session_state(colab, …)`), and the one callable behind it is the CLI funnel in `sync/cli.py`. Extraction is a dispatch change at the funnel, not a refactor of the core.
- **The venue-keyed defect is total, and it is the repo's own named defect class.** No lease record, run record, panel portion, or funnel rule carries a venue field — `grep venue` over `sync/lease/` and `sync/runner/` finds only prose in comments. Session identity is a bare Colab session name. `AGENTS.md` in this repo already rules (2026-11-12) that anything that cannot name its venue is a defect against the coexistence constraint; today that is everything.
- **The caller registry is the type specimen of the local cross-cutting contract**: an untracked live file seeded from a tracked example, machinery callers as code constants, validated at every wrapper seam. The same seed/example pattern repeats for four more configs (lease, repos, notify-routes, denylist).
- **The panel is already an app in the D6 sense**: `ui/server.py` shells out to `bin/colab-lease` for every read and write and renders only the core's served `state` portions. It is the four workhorses' cleanest existing pipeline/app split.
- **Two of the harness's missing platform services touch this repo**: the gate funnel (`bin/colab-check`) is a per-invocation gate, not an automatic gate runner; and there is no backup of the state stores (`var/` lease records, `results/runs/`) beyond the auth-transient mirror.

## 2. Anatomy

**Entry points and wrappers.** `bin/` holds thin entry points over two packages. `bin/colab-lease` (427 lines) is a thin CLI over `sync/lease/`; `bin/colab-run` is a thin entry that re-exports the `sync/runner/` package name-for-name (consumers load it by path and address `cr.colab`, `load_run_record`, `TERMINAL_STATES`). Bash wrappers (`bin/colab-up`, `colab-down`, `colab-status`, parts of `colab-sh`) source `bin/_wrap.sh`: transient-state restore/capture on entry/exit (`ops/mirror_transient.py`), the `NO_PROXY` bypass for Google traffic, CLI resolution, and `gate_check` / `plan_for` helpers that delegate admission and session-name/flag derivation back to `bin/colab-lease` — name generation and shape flags live in the lease core alone. Other entries: `bin/colab-check` (gate funnel), `bin/colab-sh` (681 lines; interactive attach under sync-claim rules), `bin/colab-xfer` / `bin/colab-fs` (transfer), `bin/colab-bridge`, `bin/colab-liveness`, `bin/colab-extend-guard`, `bin/colab-harness-bootstrap` / `colab-harness-relay`.

**The CLI funnel.** `sync/cli.py` is the one module every consumer loads: `colab(*args, timeout=18000)` (guarded subprocess invocation), `colab_bin()` (resolution: `$COLAB_BIN`, else the uv tool venv, else PATH, else `${HOME}/.local/bin/colab`), `colab_env()`, and the OAuth token guard (atomic token writes, auth-required stop-and-surface). The official CLI is deliberately not on PATH; access is through this funnel only (`AGENTS.md`).

**Lease lifecycle and record shape.** The core is `sync/lease/` (~20 modules). `lifecycle.py`: `acquire` (adopt-or-create), `extend`, `extend_grant`, `adopt_orphan`, `shorten`, `release`, `ungrant`. `records.py`: the store. A lease record is one JSON file per session at `var/lease-<session>.json` (untracked `var/`), written by staged-sibling + `os.replace`:

- Core fields (written at acquire, `lifecycle.py:231-240`): `session`, `shape`, `shape_spec{gpu, tpu, high_mem}`, `rate_cu_per_hour`, `acquired_at`, `deadline`, `last_used_at`, `jobs[]`, `budget_at_acquire`.
- Stamped as applicable: `caller`, `via`, `envelope_id` (two-tier grant scope), `renew` (window leases longer than one session life), `last_pulse_at` / `last_pulse_result`, `host`, `kit`.
- `records.save_record` also refreshes a deadline-evidence projection, `var/session-evidence-<session>.json` = `{deadline, acquired_at, shape, spec, caller}`, so orphan derivation keeps an evidenced deadline if the record is lost. Torn (unparseable) record files are detected, served as findings, and quarantined by rename — never silently dropped.
- Lifecycle rules that are contract, not detail: a record is deleted only on a confirmed-absent reading or a successful stop, never on an unreadable one; adoption restores a record from evidence (renewal config, extension events), never invents one; extend/shorten move the deadline and price the delta / nothing respectively; the reaper duty (a runtime hook outside this repo, 120 s poll) enforces hard deadlines and reconciles orphans; acquire launches the detached keepalive loop + kernel pulse so a leased session never sits truly idle.

**Run records.** `sync/runner/records.py`: one JSON per run at `results/runs/<run_id>.json` — the runner's state of record — carrying `run_id`, `job`, `caller`, `session`, `state`, and `terminal_event_state`. Terminal states are exactly `complete | failed | orphaned`. A terminal transition appends exactly one `run-terminal` event to `var/ui-outbox.jsonl` (guarded by the `terminal_event_state` stamp; a resumed run announces afresh). Verbs (`sync/runner/verbs.py`, `main.py`): launch detached, `--poll` (one bounded reconcile), `--wait` (polls the local record only, zero channel use), `--resume`, `--sweep` (reconcile every non-terminal record against the live list).

**Bundle transport.** `sync/transfer.py`: chunked upload/download over the channel's exec/upload/download verbs, `.part-NNN` chunks, per-part and whole-file SHA-256 verification, resumable. Code sync is a snapshot bundle built on the origin lineage (`sync/make_snapshot_bundle.sh`; parent = current origin tip, tree = the tree being shipped), byte size + SHA-256 recorded before transfer and verified after, applied remotely by `git fetch` + `merge --ff-only` (`sync/apply_bundle_remote.py`). Data moves are decided per class by `sync/data_manifest.py` (transfer the artifact / transfer its driver and regenerate / regenerate from the network, route recorded).

**The gate funnel.** `bin/colab-check` (229 lines): resolves the caller claim exactly as `colab-run` does (flag over `$COLAB_CALLER`, validated against the registry before anything starts), takes the target repo from the repos registry (no repo named in the file), ships the tree by snapshot bundle, and runs `check.py` remotely with the probed worker count; returns verdict + wall time. The session shape gate itself is `sync/lease/gate.py`: `check_session_admission` / `enforce_session_admission` over the `session_gate` policy block — agent actors may create High-RAM CPU sessions only; refusals, bypasses, and mismatches are journaled (`var/` gate journal) and served in `state`.

**Placement rules.** There is no session pin in the funnel. `acquire`'s adoption pool (`lifecycle.py:80-98`) sorts live records at the requested shape by: caller's own leases first, unattributed next, non-degraded before degraded, latest deadline last-key — i.e. latest-deadline adoption. A `--prefer-session` pin names a lease to adopt only; it cannot combine with create and refuses on shape mismatch or a dead/past-deadline record. Synchronous attaches are a separate claim system (`sync/lease/syncclaims.py`): a TTL'd claim held by the session's sole active caller; callers marked `active` in the registry are refused sync attaches outright (detached-only).

**The panel.** `ui/server.py` (704 lines, stdlib HTTP, 127.0.0.1:8793). Reads: `GET /api/state` and per-portion `GET /api/state/<portion>` — the portions are `sync/lease/state.py`'s served shapes (`state_records` with the access list riding it, `state_specs`, `state_budget`, `state_grant`, `state_meta`, `state_orphans`, `state_extend_guard`) — plus `GET /api/outbox` (reads never acknowledge). Writes: `POST /api/lease/{start, stop, extend, adopt, shorten}`, `/api/access/release`, `/api/grant`, `/api/grant/extend`, `/api/ungrant`, `/api/config/budget`, `/api/server/restart`. Every handler shells out to `bin/colab-lease` (`run_core`); the server renders only served state and is the single writer of `var/ui-outbox.jsonl` apart from the runner core's `run-terminal` appends. Served-record shaping happens in the core, not the panel: `state.status` widens the stored record with the pruned live-jobs projection and detached activity on read, leaving the on-disk record untouched. Panel starts carry `acquire --create` (creations, never adoptions — operator ruling in `AGENTS.md`).

**Deploy plumbing.** `ui/deploy.sh`: syncs the artifact sources to `$LEASE_UI_RUNTIME_DIR`, then publishes via the hatchlet CLI to the Library (space slug `colab-lease-2`, `platformVersion: 25`); `check` mode is a read-only drift check (exit 3 on any drift) so repo, staging, and Library cannot silently diverge. Deploy never runs tests. Local serving is supervised by a systemd unit (`ui/colab-lease-ui.service.tmpl`, `ui/ui.sh`, `ui/watchdog.sh`, `ui/stackdump.py`).

## 3. The adapter seam

The contract operations map onto the core as follows; in every case the venue work is done by the injected `colab` callable and the policy around it is venue-neutral:

| Contract op | Where it lands | Venue-shaped part |
|---|---|---|
| acquire | `lifecycle.acquire` (adopt pool, gate admission via `gate.py`, record write) + creation through the CLI `new` verb (wrappers ride `colab-lease plan` for name + args) | Shape catalog parsed from the Colab CLI's help text (`catalog.py: parse_cli_shapes`, day-cached, `catalog_error` on format change); session names from `sync/naming.py`; CU rates |
| renew | `renewal.py` + reaper-driven renewal under the same deadline for window leases (`renew: true`) | CLI session re-creation; remote kit reinstall (`_ensure_remote_dirs`, upload timeouts) |
| release | `lifecycle.release` + `sessions.stop_session_safe` | The stop verb itself; stops never use the `-s` flag form (broker verdict, `AGENTS.md`) |
| exec | `colab("exec", …)` — keepalive kernel pulse, provisioning, identity, bridge kit | The bridge (`sync/lease/bridge.py`, `snippets/bridge_agent.py`): a hash-signed command queue planted at `/content/bridge` in a standing lease — the most Colab-shaped subsystem in the repo |
| probe | `sessions.session_state` / `session_alive` / `live_sessions`, `health.py`, `catalog` | Endpoint host grammar: `sessions._endpoint_shape` reads the shape class out of Colab endpoint hostnames (`m-hm-*` = high-RAM, `m-s-*` = standard) — a second venue has no such names |

**Venue-neutral core** (carries over as-is): the record stores and their write discipline, caller validation, gate policy engine, placement sort, budget accounting structure, spend attribution, run-record machinery and its outbox event, transfer chunking + hash verification (the verbs it rides change, the protocol doesn't), and every served shape in `state.py`.

**Where a second adapter plugs in**: at `sync/cli.py`'s `colab()` — the funnel is already the single resolution point, and the core already receives the callable by injection. A per-venue dispatch behind that callable (plus a per-venue shape catalog and a per-venue stop/exec verb set) is the whole adapter surface. The lease core would not change shape.

**Cannot name its venue (defects against the venue-keyed constraint)**: everything, today — no `venue` key on lease records (`lifecycle.py:231-240`), none on run records (`sync/runner/records.py`), none in any `state.py` portion, and session identity is a bare Colab session name that a second venue's names could collide with. The repo's own `AGENTS.md` carries the ruling and the negative near-term rule (nothing new may deepen a single-venue assumption) precisely because the current state is uniformly single-venue.

## 4. Cross-cutting contracts designed locally

**The caller registry (type specimen).** Three homes, three natures:

- **Live registry — untracked** `config/callers.json` (gitignored, seeded by hand from the example): shape `{callers: [thread caller ids], active: [caller ids]}`. The live file on this machine carries 14 thread callers — including the sibling workhorses' handles (`workbench-viewer`, `owner-attention`, `scheduler-cron`) — and marks three programme-b threads `active`. Operator-written only; no code writes it.
- **Tracked seed** `config/callers.example.json`: same shape with fictional callers (`alpha-thread`, `beta-thread`, empty `active`), and the `_about` text that documents the semantics.
- **Machinery callers — code constants** `sync/lease/callers.py`: `MACHINERY_CALLERS = (PANEL_ACTOR, GATE_DEFAULT_INFRA_ACTOR, "test", "lease")` = `("panel", "standing", "test", "lease")` (constants in `sync/lease/foundation.py`), so a missing local registry never breaks the panel or the duties.

Semantics (`sync/lease/callers.py`): a claim is `--caller` on Python entry points or `$COLAB_CALLER` for bash wrappers/drivers, flag over env, resolved by `resolve_caller` and validated by `validate_caller` against `caller_registry()` (machinery ∪ local file; a missing/malformed file yields the machinery set alone — fail-closed for thread claims, never a crash). A caller may carry one lane suffix (`base:lane`), validated against its registered base. A presented-but-unregistered claim is refused at claim time (`caller_claim_error`); an absent claim leaves the call unattributed. The `active` list is a standing owner marking: an active caller's work is detached-only, and the sync gate refuses its synchronous attaches outright (`syncclaims.py`). Attaches are journaled to `var/caller-claims.jsonl` (`append_caller_claim`) — the attribution evidence for sessions that live outside lease records, and an input to session-name uniqueness.

**The same pattern, four more times** — each is a local contract the consolidation must plan, not copy:

- `config/lease.json` (untracked; seed `config/lease.example.json`): caps and policy — `daily_cu_budget` / `monthly_cu_budget`, `default_shape`, `session_gate` (agent classes, bypass actors, infra actor), `standing`, `keepalive`, `extend_guard`, `sync_claim`, `auto_acquire`. Read per invocation via `foundation.load_config`; the panel's budget editor writes caps through `bin/colab-lease budget-caps`.
- `config/repos.json` (untracked; seed `config/repos.example.json`): `sync/repo_registry.py` — pointer-only target-repo registry (`clone_url`, `local_path`, `dest`, `venv`, `init`, `version_checks`, `scan_roots`); package specs in an entry are rejected by validation (a repo's spec lives in its own `init_venv.py`). Remote side: env builds merge one record per built clone into `/content/env-registry.json` on the VM.
- `config/notify-routes.json` (untracked; seed `config/notify-routes.example.json`): caller → chat routing for the session-liveness escalation; machinery and unknown callers fall back to `main`. Its own `_comment` records that the escalation body itself lives in the scheduler repo (`bodies/colab-liveness.md`).
- `config/denylist.txt` (untracked): personal literals for the portability guard. And the negative instance: `config/profiles.json` is retired by ruling and must not exist — records are read only in the shape/caller vocabulary they are written in today.

**Spec/supervision kit copies.** `AGENTS.md` carries the synced inline block `<!-- spec-sync:supervision-rules --> … <!-- /spec-sync:supervision-rules -->` — generic supervision text synced from the spec-driven starter's `docs/supervision-rules.md`, duplicated by the sync mechanism rather than hand-copied, followed by this repo's own contract prose (the long binding-rules list in `AGENTS.md`, mechanics canon in `docs/lease-workflow.md`). The venue-keyed ruling itself sits in `AGENTS.md` as repo-local text recording the owner's 2026-11-12 decision.

**Harness registration.** `workbench.yaml` (tracked): `name`/`slug: colab-runner`, `registry: workbench/registry.db`, `plans: .plans`, `mockups: workbench/entries`, `archive: workbench/archive` — the workbench harness's registration of this repo; `.plans/` and `/workbench/` are gitignored working state (the harness runs on the files, not the git index).

## 5. Pipeline vs apps

**Pipeline layer**: the lease core (`sync/lease/` — leases, gate, placement, spend, renewal, reap, orphans, sync claims), the runner (`sync/runner/` — launch/poll/wait/resume/sweep over run records), transport (`sync/transfer.py`, bundle build/apply, `sync/data_manifest.py`), the gate funnel (`bin/colab-check`), the registries as contracts (callers, repos, lease config), and the liveness-entry generator (`sync/liveness_entry.py`). Venue/lease execution is a named pipeline engine, and this repo is almost entirely that engine.

**App surfaces**: the panel (`ui/`) — a pure consumer of `bin/colab-lease`'s served shapes — and the `bin/colab-lease` CLI itself as the operator surface. The bridge console surface rides the panel/outbox, not a separate app.

**Missing platform services, as they touch this repo**: no automatic gate runner (the gate is a verb consumers invoke); no deployment/release record of the runner's own (the panel's deploy has a drift check but no release ledger); no backup of `var/` or `results/runs/` — the only mirrored state is the auth transient (`ops/mirror_transient.py`, `config/transient.json`), which exists so a VM replacement doesn't lose the OAuth token, and it is explicitly never a blind copy-back.

## 6. Overlaps with the other three workhorses

- **Scheduler — code-level, two seams.** (a) `sync/liveness_entry.py` machine-writes scheduler job entries: for each live lease it renders `<workspace>/scheduler/jobs/colab-liveness-<session>.yaml` (15 m scripted entries running `bin/colab-liveness <session>`, `owner: none`, `self_removal` text stating the lease core deletes the entry in the same call that deletes the lease record; the sibling path resolves via `Path.home() / "workspace" / "scheduler" / "jobs"`, overridable by `COLAB_LIVENESS_JOBS_DIR`). (b) `sync/harness.py` is a client of the scheduler repo's harness connector: it mints connector tokens by running the scheduler's `bin/sched connector-token` (`SCHEDULER_REPO` = `$HARNESS_SCHEDULER_REPO` or `<workspace>/scheduler`) and stages the venue client from there. Also `ops/github-sync.md` records that this repo's GitHub pushes ride the scheduler ops route, and the liveness escalation body lives in the scheduler repo (see §4, notify-routes).
- **Workbench — registration-level.** `workbench.yaml` (above) is the overlap: the harness tracks this repo's plans/todos/mockups from the repo's own files. The liveness entry's `migration_note` records it was modeled on the workbench harness's progress entries (which stay harness-consumed and unmigrated). No code here reads workbench records, and no workbench code shape is duplicated — run/lease records are the runner's own store.
- **Owner-attention — attribution-level only.** No code reference to attention exists in the repo (grep-verified outside tests). The overlap is that attention's thread is a registered caller in the live `config/callers.json`, and attention consumes runner state through its own threads, not through a code seam.
- **Panel vs viewer shells.** `ui/` is a fourth standalone server + static shell with its own deploy-to-Library plumbing (`ui/deploy.sh`, space slug `colab-lease-2`) and its own `ui/static/theme.css` — the shell duplication the superapp inventory already names; the panel's distinction is that it is a disciplined consumer (shells out to the core for everything) where the other viewers vary.

## 7. Consolidation notes

**Preserve exactly** (formats and semantics other systems already depend on):

- Lease record JSON shape, per-session file naming (`var/lease-<session>.json`), the staged-sibling atomic write, and the `session-evidence-` projection — readers read records "exactly as written" (`AGENTS.md`), and orphan derivation, spend, and the panel all parse this shape.
- Run record shape, the three terminal states, and the exactly-one `run-terminal` outbox event (`var/ui-outbox.jsonl`) — the notify hook announces from it.
- Caller attribution semantics in full: flag over env, registry validation with machinery constants, lane suffixes, presented-but-unregistered refusal, absent = unattributed, `active` = detached-only, the claims journal.
- Placement: latest-deadline adoption, adoption-only pins, no pin in the run/gate funnel.
- Spend attribution: counted from this repo's own lease segments, never derived from account-balance deltas.
- Snapshot-bundle lineage: built on the origin lineage, size + SHA-256 recorded and verified, applied ff-only.
- The seed/example config pattern itself: tracked fictional examples, untracked live files, gitignore entries that document why each live file is local.

**The extraction must carry**: the `sync/cli.py` funnel as the adapter injection point (with its token guard decided as adapter-side auth); a per-venue shape catalog replacing CLI-help parsing; a venue key stamped on lease records, run records, and every served portion from the first extracted write (with pre-extraction records defaulted to Colab explicitly, not silently); the bridge as a Colab-adapter subsystem, not core; and the registries (callers first) re-homed as pipeline contracts with their untracked-live-file nature intact.

**Stays in this repo untouched**: the repo itself, per the ruling — the generic core is extracted alongside it. The Colab payload material stays with the Colab adapter by nature: `snippets/` (keepalive, bridge agent, session provisioning, job harness kits planted on the VM), `probes/`, and the repo's own `jobs/` manifests.

## 8. Risks and unknowns

- **Live-record migration**: every existing lease/run record lacks a venue field; the first venue-keyed writer must define how legacy records read (default-to-Colab is the obvious rule, but it is a rule someone must state, and a mixed fleet makes a wrong default expensive).
- **Catalog fragility**: the shape catalog is parsed from the Colab CLI's help text; a format change degrades the fleet to CPU shapes with a `catalog_error`. A second venue needs a catalog source that isn't help-text scraping, and the core's shape vocabulary (`gpu`, `tpu`, `high_mem`, CU rates) is Colab-denominated — budget caps and rates have no venue-neutral unit today.
- **Session-name collision**: names are unique against live sessions + records + the claims journal, all read through the Colab channel; a mixed fleet needs namespacing the current scheme doesn't have.
- **Duties outside the repo**: the reaper hook and the notify hook are registered with the runtime's hook system, not in this repo, and the liveness entries live in the scheduler's registry — the mega repo inherits three external registrations whose re-homing is not recorded in this repo's files.
- **Untracked state is machine-local**: the live registries and `var/` exist only on this machine and are not in git; any consolidation step that starts from the tracked tree alone will silently lose the caller registry, the lease config, and the repos registry unless they are re-seeded deliberately.
- **Unknown**: whether the panel's served portions are consumed by anything besides `ui/static/` (no in-repo consumer besides the panel was found; external consumers would be invisible to this review).
